# 0005 渲染路径还有多少余量（2026-11-19 实测）

状态：结论已定，等真有 4K 现场再动手。

## 三个参照实现怎么做的

| | 装饰 | 模糊 | 底衬 / 损伤 | 显存策略 |
|---|---|---|---|---|
| Hyprland | 窗口 + 装饰合成到同一张 pixmap，画的时候用 mesh（顶点位移） | 降采样到 `blur_size` 指定的分辨率再做 kawase，passes 可配；小窗口自动少几趟 | damage ring：一圈矩形，合并后只重画那块 | 缓冲池复用，按需重建 |
| KWin | 窗口 + 装饰同一张 pixmap，wobbly 直接对 pixmap 做顶点形变 | mipmap 链，按半径选层数 | 每个窗口一份 damage region，pixmap 增量更新 | 每个窗口一主一备两张 |
| niri | 无装饰（客户端自绘），直接合成 | 无 | damage + 直接扫描输出（plane） | 单一渲染目标、按输出复用 |

Vidow 现状：装饰 + 内容同一张离屏（同 KWin），模糊金字塔按窗口建（同 KWin/Hyprland），
底衬私有/共享两档（KWin 没有这一档），损伤按屏框合并（还没有 KWin 的每窗 region）。

## 实测：这三条路在本项目里还剩多少

场景 headless 双屏（1280x720 + 3840x2160 scale 2），`tools/perf-scene.sh`。

### 1) 显存（对应「小窗降层级 / 金字塔裁剪」）

用 `VIDOW_MEM_TRACE`（临时探针，已删）统计一次 6 窗场景的**全部**分配：

| 尺寸 | 块数 | 合计 |
|---|---|---|
| 649x724（装饰） | 6 | 10.8 MB |
| 1280x720（共享底衬） | 1 | 3.5 MB |
| 768x768 / 768x640（私有底衬） | 2 | 4.1 MB |
| 640x360（模糊金字塔第一级） | 2 | 1.8 MB |
| 其余（各级金字塔、动画、果冻） | — | 10.6 MB |
| **合计** | | **30.8 MB** |

`vram_own` 那个指标报 195 MB，是 **fdinfo 里同一个 GBM bo 被多个 handle 重复计数**
（ADR 0002 已记过）。真实占用 30 MB 量级，6 个窗口 —— **降层级 / 金字塔裁剪只能省个位数 MB**，
不值得动视觉效果。

### 2) 趟数（对应「按损伤矩形重烘」）

- 6 窗场景：32 趟/帧（装饰 6 + 金字塔各级 + 输出合成），装饰重烘 0.14 ms/帧，模糊 <0.05 ms/帧。
- 整帧 16.6 ms 里，果冻 + 模糊 + 装饰 + 提交合计 0.31 ms（ADR 0002 已量过）。

结论：**按损伤矩形重烘只能省下那 0.14 ms 里的一部分**。打字 / 小区域更新时确实有用，
但这不是 4K 卡顿的成因。

### 3) GPU 与损伤

- `gpu_busy_percent` 2–3%，损伤 20%/帧，fps 62。
- 4K 屏整屏合成一次约 1.6 ms 量级（`multiscreen` 在 3840x2160 那块上的份额），
  4K + 整屏损伤才是真正花钱的地方 —— 这条需要真机会话的数据才能定性。

## 结论

1. **不走 draw-pass**（已 revert）：它省 11 趟/帧，但和直通互斥、整屏重绘，4K 下更贵。
2. **显存优化没余量**：真实占用 30 MB，指标 195 MB 是重复计数。
3. **损伤重烘余量小**：装饰 0.14 ms/帧的上限摆在那儿。
4. 下一步要花在**整屏合成与损伤**上（KWin 的每窗 damage region + niri 的 plane 直扫
   我们能做的是前者）：把「整屏 20% 损伤」压成「只有真变的那几个矩形」，
   并用真机 4K 会话取数 —— 合成器自己的探针只覆盖 1.8%，必须看外部的
   `gpu_busy_percent` 与帧时。

## 想动手时从哪儿开始

1. 真机 4K 上开 `VIDOW_STUTTER=1`（配置里的 `stutter` 键），拖一个大窗 + 视频播放，
   收 `卡顿:` 行 —— 有数字再谈优化。
2. 若确实是整屏合成：把 `vidow_arrange` 之后的损伤从「整屏一块」拆成每窗 region，
   再按 region 合并成 ≤4 块（Hyprland 的 damage ring 思路）。
